# Workshop Feedback Portal — Data Model (POC)

Status: Design
Owner: Solution Architect
Source of truth: `docs/requirements.md`, `WORKSHOP_CONSTRAINTS.md`
Companion: `docs/architecture.md`, `docs/api-contract.md`

Defines the logical persistence model and approved access patterns for the single application data store: a DynamoDB table. Precise enough for Backend and DevOps to implement consistently. DynamoDB is schemaless at the storage layer; the logical schema below is authoritative.

---

## 1. Store overview

- **Service:** Amazon DynamoDB (approved catalog).
- **Table (logical name):** `Feedback`.
- **Capacity mode:** `PAY_PER_REQUEST` (on-demand) — NFR-008.
- **Rationale:** durable, serverless, on-demand persistence for write-once feedback records retrievable by organizers (FR-004, FR-006, FR-007, NFR-012, NFR-014).

---

## 2. Entity: Feedback record

One item per submitted, validated feedback submission. Records are **write-once** (no update/delete in scope).

| Attribute | Type (DynamoDB) | Logical type | Required | Ownership | Description |
|-----------|-----------------|--------------|----------|-----------|-------------|
| `feedbackId` | S | UUID string | Yes | Server-generated | Unique identifier for the record; **partition key**. Generated by Lambda (UUIDv4) at accept time. |
| `workshopId` | S | string | Yes | Client-supplied (validated) | Workshop identifier/name. Non-empty, trimmed, max 200 chars. (BR-004) |
| `rating` | N | integer | Yes | Client-supplied (validated) | Overall rating, integer 1–5 inclusive. (BR-001–BR-003) |
| `comment` | S | string | No | Client-supplied (validated) | Optional free-text, max 1000 chars. Absent attribute when no comment provided. (BR-005) |
| `createdAt` | S | ISO-8601 UTC timestamp | Yes | Server-generated | Submission timestamp, e.g. `2026-09-05T08:34:33Z`. (FR-006, AC-002) |

Notes:
- **No PII fields** (no name/email/etc.) — records are effectively anonymous (BR-007, A-004).
- When no comment is supplied, the `comment` attribute is **omitted** from the item (not stored as empty string). The API returns `comment: null` in that case (see api-contract).
- Numeric `rating` is stored as a DynamoDB Number; Backend must enforce integer-ness at validation time.

### Example stored item (logical JSON view)

```json
{
  "feedbackId": "6f9619ff-8b86-4d01-b42d-00cf4fc964ff",
  "workshopId": "aws-serverless-2026-09",
  "rating": 4,
  "comment": "Great pacing, more hands-on labs please.",
  "createdAt": "2026-09-05T08:34:33Z"
}
```

Item without a comment:

```json
{
  "feedbackId": "a1b2c3d4-0000-4aaa-9bbb-ccccdddd1111",
  "workshopId": "aws-serverless-2026-09",
  "rating": 5,
  "createdAt": "2026-09-05T08:40:10Z"
}
```

## 3. Keys and indexes

| Element | Choice | Rationale |
|---------|--------|-----------|
| Partition key | `feedbackId` (S) | Uniquely identifies each write-once record; high-cardinality, avoids hot keys. |
| Sort key | none | Single-item-per-key model; no need to group items under a shared partition. |
| Global/Local secondary indexes | **none** | No approved query pattern requires filtering, sorting, or lookup by another attribute for the POC. Adding an index would violate NFR-009 (minimal footprint). |

## 4. Access patterns

| # | Access pattern | Operation | Trigger | Requirements |
|---|----------------|-----------|---------|--------------|
| AP-1 | Create one feedback record | `PutItem` (item keyed by generated `feedbackId`) | `POST /feedback` after successful validation | FR-004, FR-006, AC-001, AC-002, AC-007 |
| AP-2 | Retrieve all feedback records for organizer review | `Scan` | `GET /feedback` after organizer key verification | FR-007, FR-009, AC-008, NFR-012 |
| AP-3 | Point read of a single record | `GetItem` by `feedbackId` | Not required by any current requirement | (reserved; not implemented) |

- **AP-1 (write):** Lambda generates `feedbackId` and `createdAt`, then `PutItem`. Because `feedbackId` is a fresh UUID per submission, no conditional expression is needed; write-once semantics hold naturally (no update/delete in scope).
- **AP-2 (read all):** `Scan` returns the full collection. Chosen because the only read requirement is "show the collected feedback" with no filtering, sorting, or pagination in scope (see requirements out-of-scope). At workshop-sized volume (A-007, NFR-014) `Scan` is appropriate and simplest. This is an explicit trade-off (architecture ADR-4); it is not intended to scale beyond the POC.

No update or delete access patterns exist (submissions are write-once — requirements out-of-scope).

---

## 5. Validation ownership

All field constraints in the table above are enforced **server-side in Lambda before `PutItem`** (BR-008). The data store itself does not enforce them (DynamoDB is schemaless). DevOps provisions the table; Backend owns validation and item construction. Constraints match the `POST /feedback` request rules in `docs/api-contract.md` exactly:

- `workshopId`: required, non-empty (trimmed), ≤ 200 chars.
- `rating`: required, integer, 1–5 inclusive.
- `comment`: optional, ≤ 1000 chars when present.

---

## 6. Retention, durability, and privacy

- **Durability:** DynamoDB provides durable, multi-AZ persistence; records survive Lambda invocations (NFR-012, AC-002, AC-008).
- **Retention:** no retention/archival/backup policy; data exists only for the POC lifetime and is removed at `terraform destroy` (R-004, requirements out-of-scope). No TTL attribute is defined for the POC.
- **Privacy / minimization:** the model stores no PII (BR-007). Only workshop identifier, rating, optional comment, and server timestamp are persisted. Comment content is free-text and unmoderated (R-003, accepted risk).
- **Access control:** the table is reachable only by the Lambda execution role, scoped (least privilege) to `PutItem`, `GetItem`, and `Scan` on this table's ARN (NFR-006).
